# Product

## Register

product

## Users

Effect power users who want an Effect-idiomatic way to build user interfaces. They already value typed errors, dependency injection, layers, explicit effects, and composable runtime boundaries. They come to trygg to evaluate whether UI code can follow the same model instead of switching mental models at the component layer.

Their context is practical and technical: they are reading docs, scanning examples, trying the canary CLI, debugging type surfaces, or deciding whether to contribute. They need confidence quickly, then depth when they choose to keep going.

## Product Purpose

trygg is an Effect-native UI framework with JSX, fine-grained DOM updates, typed component requirements, and dependency injection built into the component model.

The website and docs should help users understand the core idea fast, install a canary project safely, learn the framework patterns, track changes, and decide whether trygg fits their Effect-based applications. Success looks like an Effect developer saying: this is how UI should compose in an Effect codebase.

## Brand Personality

Precise, effect-idiomatic, calm.

The voice should feel expert and measured. It should respect that the audience is technical without becoming academic or performatively clever. Copy should be direct, concrete, and honest about canary status.

## Anti-references

- Generic SaaS landing pages with vague productivity claims.
- React-clone framing that explains trygg only by comparison.
- Academic functional-programming presentation that feels distant from building apps.
- Purple Vercel mimicry.
- Lime-on-cream foldkit mimicry, or any other framework site whose identity is owned by a competitor.
- Mint-wash Mintlify mimicry and gradient-card OpenAI mimicry.
- Terminal-only hacker aesthetic that makes the product feel narrower than it is.
- Decorative complexity that hides the mental model or weakens navigation.
- Identical icon-heading-text card grids used to fill space.

## Design Principles

1. Make the Effect model visible. Show services, layers, typed failures, and signals through real examples rather than abstract claims.
2. Clarity before spectacle. The interface can be polished and distinctive, but it must help users orient, compare, install, and learn.
3. Teach through progressive depth. Start with the simplest runnable path, then reveal conceptual detail, API surfaces, and edge cases as users ask for them.
4. Preserve expert calm. Use confident hierarchy, restrained motion, and precise copy. Avoid hype language.
5. Treat canary status as trust-building context. Be transparent about instability while making the path to experimentation feel safe.

## Accessibility & Inclusion

Target WCAG 2.1 AA. Design and implementation should be keyboard-first, reduced-motion safe, screen-reader navigable, and usable without relying on color alone. Interactive docs and examples should keep focus states visible and preserve semantic HTML wherever possible.
